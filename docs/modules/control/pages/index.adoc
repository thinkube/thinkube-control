= Thinkube Control
:page-type: reference

_The control panel: what each of its pages does, and the operations it exposes to the agent as MCP resources and tools._

.TL;DR
You can ask your agent Code to do anything these pages do. Open Thinkube Control when you want to see the state of things or click instead of asking.

The installer deploys Thinkube Control as a core component.

== The pages

The sidebar has three groups.

image::control-dashboard-all.png[Thinkube Control with the All Services dashboard open]

=== Dashboard

[cols="1,3",options="header"]
|===
| Page | What it shows

| Favorites | The services you starred, in the order you drag them into. With no favorites, Thinkube Control opens on All Services.
| All Services | Every core component, optional component and deployed application, one card each. The logo's colour is the type (core, optional, your apps), the bar on the left is the state, and the top border carries the category and the version. A card opens the service, shows its details, stars it, and its *⋯* menu restarts it, checks its health or switches it off and on. New services appear here automatically. With Prometheus installed, a *Nodes* panel above the cards shows each node's memory, CPU and GPUs.
| Knative Services | Applications that scale to zero when idle, deployed with `type: knative`, on the same cards.
| One page per category | The same cards, one category at a time. The categories are the ones your services declare.
|===

Every card's *details* page shows the service's health status and the health history Thinkube Control has recorded for it, and carries the *Service Enabled* switch, the same as *Disable* and *Enable* in the card's menu. Switching a non-core service off scales it to zero; on brings it back. This is the switch that keeps an installed optional component from costing memory while you are not using it.

=== Deployment and infrastructure

[cols="1,3",options="header"]
|===
| Page | What it does

| LLM Gateway | The gateway endpoint, the GPU nodes with their slots and memory, the inference backends it has discovered, and every model in the registry with a *Load* and *Unload* control. xref:llm-serving.adoc[LLM serving and models] describes the mechanics.
| AI Models | The model catalogue. Mirror a model from Hugging Face into Thinkube Storage; watch the mirror job; delete a mirrored model.
| Templates | The template catalogue. Deploy a template by name or from a GitHub URL, follow a deployment's progress, publish one of your applications as a template, and delete one of your applications (see <<delete-app>>).
| Harbor Images | Two tabs. *Mirrored Images*: the public images the platform mirrored into Thinkube Registry, with their mirror date and per-architecture tags, and a control to mirror one again. *Custom Images*: images you define from a build file and build here.
| Optional Components | The catalogue of optional components with their requirements and whether each is installed. Install one; remove one. An installed component is switched off and on from its card's details page.
| Cluster Nodes | Every node with its role, architecture, memory, GPUs and version. Add nodes and remove nodes; see xref:install:adding-nodes.adoc[Add more nodes].
|===

[[delete-app]]
=== Deleting an application

On the *Templates* page, under *Your Apps*, the bin icon of an app's card deletes the app. You type the app's name to confirm. The agent does the same with the `delete_app` operation.

The delete removes what the deploy created: the Argo CD application, the app's namespace, its build template, builds and build secret, its MLflow volumes, its Keycloak client, its images in Thinkube Registry, its build logs and artifacts in Thinkube Storage, its records in Thinkube Control, and the checkout `/home/thinkube/apps/<app>`.

Two things are kept unless you tick them, because nothing can rebuild them:

* *Also delete the Gitea repository (code and history)*: the repository `thinkube-deployments/<app>`.
* *Also delete the databases*: the PostgreSQL databases of the app, `<app>` and `test_<app>`, with hyphens written as underscores.

When it ends, the dialog lists every step and its result. If a step failed, the other steps still ran, and the list says what is left. Delete the app again to retry what is left.

Only your own applications can be deleted this way. Optional components are removed on the *Optional Components* page.

=== Configuration and security

[cols="1,3",options="header"]
|===
| Page | What it does

| Jupyter Kernels | Notebook environments built from definitions. Start from the `fine-tuning` or `agent-dev` template, add packages, and build it for every GPU architecture in the cluster. A built environment appears as a kernel in Thinkube Notebooks. The two templates themselves come ready-built with Thinkube and cannot be rebuilt here; a custom environment cannot take a template's name. Deleting an environment removes it from every node.
| JupyterHub Config | The defaults a new notebook server starts with: node, CPU cores, memory and GPU count. The form shows what each node has, and the defaults cannot exceed it.
| Secrets | Secrets your applications read, and which applications use each one. Changing a value restarts those applications.
| API Tokens | Tokens for calling Thinkube Control and the LLM Gateway from outside the browser. They start with `tk_`.
| News & Fixes | News about your release, and fixes for the components on your cluster, with an *Apply* button. A bell with a count in the top bar says when there is something new. See xref:news-and-fixes.adoc[News and fixes].
|===

== Extensions

An extension is an application deployed with `deployment.type: extension`. It runs in Thinkube Control's namespace, `thinkube-control`, and Thinkube Control shows its pages in its own sidebar. See xref:ROOT:reference/thinkube-yaml.adoc#_spec_extension[spec.extension].

An extension that declares the `workflows` service runs its long work as Argo workflows in that namespace, so a restart or a redeploy of Thinkube Control or of the extension does not stop it. It gets:

* A ServiceAccount `<extension>-workflows`, which its pods run as and its workflows name.
* A Role and RoleBinding `<extension>-workflows`: create, read, list and delete workflows; report step results; read pods and their logs. Nothing more in Thinkube Control's namespace.
* Its own artifact repository: the ConfigMap `<extension>-artifact-repositories` and the Secret `<extension>-artifacts-s3`. It writes to the bucket `argo-artifacts` under the prefix `<extension>/`, so the artifacts of two extensions do not mix.
* The variables an application gets for `workflows`. `WORKFLOWS_ARTIFACT_REPOSITORY` names the ConfigMap; each workflow names it in `spec.artifactRepositoryRef.configMap`. A workflow that names no repository has none, because Thinkube Control's namespace has no default one.

The workflow's pods count against the namespace's ResourceQuota and take its LimitRange defaults when a step sets no resources. Nothing keeps them off GPU nodes: a step that needs no GPU sets a `nodeSelector` or an affinity itself.

Deleting an extension also deletes the workflows that run as its account, and its artifacts under `<extension>/`.

== The operations

Every page above is also a set of operations, each reachable from the agent by name. The agent reads the full list from Thinkube Control when it starts. Ask your agent Code what it can do; it answers from the live list.

== Calling it from outside the browser

The REST API is at `https://control.<your domain>/api/v1`, with its OpenAPI description at `/api/v1/docs`. Create a token under *API Tokens* and send it as `Authorization: Bearer tk_…`. The same token is accepted by the LLM Gateway.

Thinkube IDE arrives with this connection made: each agent's MCP configuration points at `https://control.<your domain>/mcp` with a token the installer created.
